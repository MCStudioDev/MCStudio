# Arabic facts workflow

Implementation scope: Arabic ingredient resolution, structured recipe facts, independent read-only discovery of English shared/reference/editor/trusted sources, bounded source correction and fresh generation, independent validation/cache versions, and automatic persistent Arabic pictures. English generation services, endpoints, prompts and content stores remain unchanged. The original Arabic rollout introduced three shared UI import changes in ScannerTab, HistoryTab and MealPlanTab; this source-discovery extension changes only Arabic production services. The wrapper passes English props directly to the original, unchanged MealRevealCard.

Validation sequence: regression tests first; local checkpoint after the intended RED failure; focused GREEN tests; full relevant regression/type/build checks; browser checks where a signed-in local session is available. Production activation and staging validation require a separate configured environment; neither is implied by local validation.

Storage: existing Arabic recipe/history/weekly/image collections, plus Arabic-only ingredient-resolution and reference-variant indexes. Source eligibility and content fingerprints must be checked on read and in the publication transaction. No migrations or bulk translations.

Billing: free users without generation credits discover recipes only in the validated Arabic cache. They do not trigger English-source discovery, translation or fresh generation; source-linked Arabic entries still require read-only eligibility/fingerprint checks. Premium users and free users with generation credits use the existing entitlement policy. Unresolved ambiguous inputs fail before credit reservation. Entitled generation uses one existing action reservation across bounded internal requests. Image cache hits do not consume generation grants. New images use the Arabic storage prefix.

Weekly access follows the English weekly-plan policy: free users with zero credits cannot generate or regenerate a week, including a week assembled entirely from Arabic cache. The server returns `402 FREE_AI_CREDITS_EXHAUSTED` before cache retrieval, and the UI disables generation in either language. A successful weekly action reserves and completes one shared credit for a free user, whether its meals are cached, generated or mixed; premium/admin access remains exempt through the existing billing service. Incomplete/failed weeks release the reservation. Saved-plan reads remain available, and zero-credit scanner requests can still use validated Arabic recipes. This supersedes the earlier cache-only weekly access and successful-week refund behavior described in historical verification below. English server and billing code are unchanged.

Weekly-access verification (2026-09-18): 321 tests passed across 34 Arabic, UI and English weekly-contract suites, including zero-credit direct requests with empty/full pools, reservation-time credit exhaustion, one action per cached week, failed-week release, free scanner cache access and premium/admin controls. ## Generation and validation

1. Authenticate, load saved restrictions, normalize English/Arabic/mixed ingredients, and apply an Arabic request bucket. Local food identities are derived from existing dictionaries, the taxonomy, ingredient knowledge graph and cuisine catalogs. They do not modify those sources.
2. Unclear input can use one bounded semantic resolution request for entitled users. It must select an existing food ID at high confidence. Cache that resolution only in `ingredientResolutionsArabicV1`; free users can read it. Ambiguous shawarma protein always requires clarification.
3. Revalidate Arabic recipe candidates. If entitled results are short, independently read eligible English shared recipes, references, unexpired editor semantic-cache entries and the bundled trusted catalog. An editor entry can resolve its source without a reference-search hit. These readers never repair, promote, normalize, warm or write English records. Source-linked Arabic variants use `recipeVariantsArabicV1`.
4. The server selects diverse dish identities and issues stable `candidateId` values. Source correction receives only its assigned sources, without general cuisine suggestions. Fresh generation receives catalog candidates grouped by ingredient family, with duplicate English/native names and recent dishes excluded; uncatalogued cuisines use bounded discovery slots. Catalog manifests must retain their known essential ingredients. Source correction and fresh generation start concurrently under the same action/deadline. Preparation manifests include declared cooking actions; the server includes required operational water before checking the missing limit. Complete over-budget source dishes may become shortage suggestions, never matching recipes. There is no Egyptian/vegan special branch.
5. Generate one structured facts object per accepted manifest. Both paths use exact food IDs and named step IDs (`s1`…`s30`) with `previousStepIds`; the adapter resolves these into the existing stored `previousSteps` representation. Unknown, duplicated, self or future references fail validation. Candidate IDs keep names, ingredients and source links attached even when outputs are omitted or reordered. The server renders internal English and visible Arabic from the same amounts, states, instructions and nutrition. Existing quantities, states, nutrition and source links are immutable during repair. A repair may add only measured plain water when a later preparation exposes missing operational liquid; the complete result is verified again and that water counts toward the user's missing limit.
6. Run unchanged pure dietary/health checks plus Arabic property, language and preparation checks, including measured soaking water and cooking-liquid references. Independently review culinary identity, states, quantities and ordered preparation for every new recipe. Unknown labels and unclassified ingredients require semantic verification; independent food-category/compound classifications are also checked by deterministic dietary rules, so a blanket `safe:true` cannot override an incompatible category. Receipts bind to facts and effective restrictions. Keep successful dishes while one bounded repair round handles only failed preparation candidates, with one isolated schema/request per failed dish, followed by fresh verification. Each repair schema exposes only that dish's food IDs (plus plain water when explicitly authorized by the server). Ingredient, nutrition or identity failures that cannot be safely fixed remain rejected.
7. Deduplicate validated recipes; return safe partial results with shortages when appropriate. Weekly generation uses three parallel meal-slot batches under one action/deadline. Catalog meal types deterministically distribute flexible dishes across those batches; discovery slots are scoped to the meal type, preventing the same candidates from occupying all three batches. Prefer 21 distinct compatible meals; after a bounded top-up when time permits, allow at most two repeated slots (the English fallback's less-than-10% limit). Save only after filling every slot, building an Arabic shopping list from all 21 validated servings and checking the complete plan.

Shopping quantities aggregate by ingredient, preparation state and compatible unit dimension. Measured pantry stock is subtracted once. The adapter does not invent package weights, food density or raw-to-cooked conversions. Existing validated Arabic recipe pairs and fractional quantities remain readable.

Arabic requests retain the configured Gemini model/transport, with bounded attempts and a deadline that respects Gemini's minimum request timeout. Internal planning, resolution, verification and repair do not create additional app actions.

Source discovery is deliberately bounded: shared ingredient lookup reads at most 50 records, semantic lookup queries the newest 200 unexpired entries, and ranking hydrates/returns at most 20 candidates. It searches all supported source types, not every record on each request. Semantic entries require the current editor cache version and a still-eligible original source. Shared search aliases are not recipe ingredients. The route selects at most three source candidates and concurrently starts fresh generation, reserving five seconds for publication. Each fact batch reserves time for independent verification; repair runs only with enough time for another verification. At most one productive top-up is allowed. Identical in-flight correction requests share work; different restrictions remain separate.

Per-dish selection, planning, generation, verification, repair and publication outcomes are logged with the request ID. Successful Arabic history stores a bounded `generationDiagnostics` array (up to 150 entries) containing dish identifiers/names and stable reason codes, not raw prompts or provider output. Complete failures log diagnostics without replacing existing results. Partial/repeated results explicitly explain failed validation or generation when relevant. Existing billing, source/image fingerprints and image namespaces are retained. No English production file or data destination is changed by this extension.

Source pointers identify `shared`, `reference` or `trusted` origins and bind their content fingerprint. Semantic derivatives additionally bind the editor key, recipe fingerprint, version and expiry. These checks run again before publication, Arabic reuse and photo reuse. Stale or blocked derivatives are rejected without repairing or deleting their English sources. Prompts receive only recipe content; cached image tokens and user-specific ownership metadata are excluded.

## Recipe variation on repeated clicks (2026-09-13)

Arabic scanner generation now follows the English fresh-first concept, implemented entirely in Arabic services. For the same normalized ingredient set, each request reads up to 100 recent Arabic history entries and prioritizes dishes not shown during the last 24 hours. English, Arabic and mixed pantry spellings resolve to the same context. New Arabic history records include versioned dish keys; older Arabic history is interpreted at read time without migration. Weekly-plan selection is unchanged.

Each click supplies a new action seed to rotate equivalent cache candidates and fresh Gemini generation. The Arabic cache lookup considers up to 200 matches. Entitled users can fill shortages through eligible English-source correction and then fresh Arabic generation, with previous dish names excluded. Previously shown sources are filtered before source selection; source corrections retain their existing in-flight sharing when inputs match. Free users without AI credits use only the validated Arabic cache.

If fresh options cannot fill the requested count, the response appends revalidated recent recipes, preferring the least recently shown. Each repeat carries `freshness_origin: "backfilled_recent"`, and the Arabic status message reports new/reused counts. This cannot guarantee unlimited unseen dishes in a finite compatible cache. Dietary, cuisine, missing-ingredient and source-eligibility checks still apply to every result. An unavailable history read times out after five seconds and returns matching results with an explicit freshness-unavailable message rather than claiming they are new.

If AI adds no accepted fresh recipe, its reserved action is released and no new image grant is issued. Reused recipes keep their Arabic IDs and existing image-cache associations. All variation metadata is written atomically with the result to `users/{uid}/historyArabicV1`; no English history, recipes, cache, images or endpoints are changed.

Verification: 213 Arabic tests passed across 27 files, plus 90 existing English/profile/UI tests. An additional scanner case verifies distinct per-click action IDs and the full-count repeat message. The freshness module has 100% statement and 97.36% branch coverage. Scoped ESLint, TypeScript and the final production build passed; the build retains the existing English artifact-loader tracing warning. Local tests mock Firebase and AI providers; no live account generation, account-setting change, credit consumption, push or deployment was performed.

## Image behavior

The Arabic photo endpoint previously used the undefined `recipe_image` rate-limit name. It now uses the existing photo-limit configuration with an Arabic-only bucket. The rate limiter's English configuration and buckets are unchanged.

The Arabic card automatically requests a photo when visible, shows a useful failure/retry message, and restores images by Arabic recipe ID in scanner, history and weekly-plan views. English cards do not enter that component's network path.

Eligible English source images and editor images may be reused read-only for shared, reference-linked editor and trusted sources. Reuse requires matching dish identity, compatible diet, matching structural ingredients and current source fingerprints; unclear ingredient identities prevent reuse. Corrections that change the dish cannot borrow its old photo. New images use a separate literal recipe-facts prompt and the configured Replicate transport settings. This avoids the shared fuzzy prompt builder remapping a dish to a nearby identity. New images persist under `arabic-recipe-photos-v1/` with a durable association in `recipePhotoCacheArabicV1`. A transaction lease coalesces workers; existing validated photo hits do not regenerate or consume grants. Polling URLs and downloaded image origins/types/sizes are checked. Source eligibility is rechecked before publication.

`ar-image-v2-facts` identifies the Arabic image prompt. Earlier Arabic generated-photo cache entries without that receipt are refreshed on demand; there is no bulk image job. English photos and their receipts are untouched.
